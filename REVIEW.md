# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` | Does not actually ping MongoDB — always returns `{"status":"ok"}` even when the database is down. Contract requires 503 when MongoDB is unreachable. | Start the app with MongoDB stopped; `GET /health` returns 200 instead of 503. | Added `client.admin.command("ping")` inside a try/except, raising `HTTPException(503)` on failure. |
| 2 | `create_employee()` line 79 | **Race condition (check-then-insert).** `find_one` + `insert_one` is not atomic — two concurrent requests with the same `emp_code` can both pass the check and both insert. | Send two identical `POST /employees` requests simultaneously; both return 201, and the collection has duplicates (or one silently overwrites). | Created a unique index on `emp_code` at startup and catch `DuplicateKeyError` to return 409. Removed the `find_one` guard. |
| 3 | `create_employee()` line 82 | `datetime.now()` creates a **naive datetime** (no time zone). MongoDB stores it without tz info, making it ambiguous and inconsistent with the rest of the system. | Compare `created_at` values written on servers in different time zones — they drift. | Changed to `datetime.now(timezone.utc)`. |
| 4 | `create_employee()` line 85 | Returns the raw document with `created_at` as a Python datetime object, not epoch milliseconds. The contract requires all instants to be integer epoch ms. | `POST /employees` returns `"created_at": "2026-07-06T..."` (ISO string or datetime repr) instead of an integer. | Added `format_employee()` that converts `created_at` to epoch ms via `datetime_to_epoch_ms()`. |
| 5 | `create_employee()` | No validation that `shift_start != shift_end`. The contract says they must differ. | Create an employee with `shift_start == shift_end`; no error, but downstream calculations (overtime, late) break. | Added an explicit check, returning 422. |
| 6 | `list_employees()` line 93 | **Wrong skip calculation:** `skip = page * page_size`. Page 1 skips the first `page_size` items — the first page of results is never returned. | `GET /employees?page=1` returns the *second* page. | Changed to `skip = (page - 1) * page_size`. |
| 7 | `list_employees()` line 94 | `total = db.employees.count_documents({})` — counts the **entire collection**, ignoring the `department` filter. | Filter by department "Sales" (2 employees), but `total` says 6. Pagination metadata is wrong. | Changed to `count_documents(q)` so the total reflects the filter. |
| 8 | `list_employees()` | No sort order. The contract requires ascending `emp_code`. | Results come back in insertion order, which may vary. Grader checks exact order. | Added `.sort("emp_code", ASCENDING)`. |
| 9 | `list_employees()` line 95 | Returns raw datetimes for `created_at` instead of epoch milliseconds. | Same symptom as defect #4: `created_at` is a datetime, not an int. | Applied `format_employee()` to each item. |
| 10 | `list_employees()` | No validation on `page` (min 1) or `page_size` (1–100). | `page=0` or `page_size=999` are silently accepted. | Added `Query(1, ge=1)` and `Query(20, ge=1, le=100)`. |
| 11 | `punch_in()` line 101–102 | **No 404 for unknown employee.** If `find_one` returns `None`, line 113 crashes with `TypeError: 'NoneType' object is not subscriptable`, producing a 500. | `POST /attendance/punch-in` with a non-existent `emp_code` returns 500 instead of 404. | Added an explicit `if not emp: raise HTTPException(404, ...)`. |
| 12 | `punch_in()` line 102 | `datetime.fromtimestamp(…/1000)` creates a **naive datetime in the server's local time zone**, not UTC. All downstream calculations (date, late, overtime) are wrong unless the server happens to be in UTC. | Run the server in IST (UTC+05:30); the stored `punch_in` is offset by 5.5 hours compared to UTC. | Changed to `datetime.fromtimestamp(…/1000, tz=timezone.utc)` (wrapped in `epoch_ms_to_datetime`). |
| 13 | `punch_in()` line 103 | **Attendance date is computed in server local time**, not IST. `ts.date()` uses whatever timezone `ts` is in (which is local, per defect #12). Contract says date = IST calendar date of punch_in (R1). | Server in UTC: a punch at 23:30 UTC (05:00 IST next day) gets the wrong date. | Converted to IST before extracting the date, in `get_attendance_date()`. |
| 14 | `punch_in()` line 103 | **No overnight-shift handling.** R1 says for overnight shifts, a punch-in before `shift_end` belongs to the *previous* day. The starter ignores this entirely. | Employee with shift 22:00–06:00 punches in at 23:00; the date is the IST calendar date. But at 03:00 it should roll back one day, and it does not. | `get_attendance_date()` checks for overnight shifts and adjusts. |
| 15 | `punch_in()` line 104 | **Race condition (check-then-insert).** Same pattern as defect #2: `find_one` then `insert_one`. Two concurrent punch-ins for the same employee and date can both succeed. | Two simultaneous `POST /attendance/punch-in` for the same employee and day both return 201. | Rely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError` → 409. |
| 16 | `punch_in()` line 119 | Returns `"id"` field (stringified `_id`) which is **not in the API contract**. `_id` must never appear in responses. | Response body contains `"id": "668..."` — grader may flag unexpected fields. | Removed the `doc["id"]` line; `format_attendance_record()` excludes `_id`. |
| 17 | `punch_in()` | Does not validate that `status` is one of `PRESENT`, `WFH`, `ON_DUTY`. Accepts arbitrary strings. | `POST /attendance/punch-in` with `status: "INVALID"` succeeds. | Added a check against `PRESENCE_STATUSES`, returning 422. |
| 18 | `punch_in()` | Does not truncate the timestamp to whole seconds (R1 requires it). Sub-second precision leaks through. | `punched_at` with fractional seconds is stored and returned as-is. | Wrapped in `truncate_to_seconds()`. |
| 19 | `punch_in()` | Response body contains raw Python datetimes for `punch_in`, `punch_out`, etc. instead of epoch milliseconds. | Response has datetime-like strings instead of integers. | Applied `format_attendance_record()`. |
| 20 | `compute_late_minutes()` line 35 | **Timezone mismatch.** `punch_in.replace(hour=h, minute=m)` replaces the UTC hour/minute with the IST shift-start hour/minute. Example: punch at 04:35 UTC (10:05 IST), shift 09:30 → `start` = 09:30 UTC (15:00 IST). Difference is −295 min → returns 0 (not late). But the employee IS 35 min late. | Any employee with a non-UTC-friendly shift (most of them) is never detected as late. | Converted `punch_in` to IST first, then replaced hour/minute, so the comparison is in the same timezone. |
| 21 | `compute_work_hours()` line 41 | Uses Python's built-in `round()`, which applies **banker's rounding** (round-half-to-even). R4 requires half-up. | `round(8.545, 2)` → `8.54` (banker's) instead of `8.55` (half-up). | Replaced with `round_half_up()` using `Decimal.quantize(ROUND_HALF_UP)`. |
| 22 | `compute_overtime()` line 47 | **No 30-minute minimum.** Returns any positive number of minutes, but R3 says overtime counts only when ≥ 30. 5 minutes past shift-end reports 5, should be 0. | Employee leaves 10 min after shift-end → `overtime_minutes` = 10 instead of 0. | Added `return minutes if minutes >= 30 else 0`. |
| 23 | `compute_overtime()` line 46 | **No overnight-shift handling.** Builds `shift_end` on the attendance date, but for an overnight shift (22:00–06:00) the end falls on the *next* calendar day. | Overnight employee: shift_end 06:00 is placed on July 6 instead of July 7 → huge negative overtime → returns 0 forever. | Detect overnight (`shift_end ≤ shift_start`) and add one day to the end datetime. |
| 24 | `list_attendance()` line 144 | **Loads the entire collection into memory** (`list(db.attendance_logs.find(q))`), then sorts and paginates in Python. With 100k records this is extremely slow and memory-hungry. | Endpoint response time degrades linearly with collection size; may OOM. | Used MongoDB `.sort().skip().limit()` and `count_documents()` so only the current page is fetched. |
| 25 | `list_attendance()` line 145 | Python-side sort uses only `date` (desc). Contract requires secondary sort on `emp_code` ascending for ties. | Two records on the same date appear in arbitrary order. | Changed to `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| 26 | `list_attendance()` line 149 | Returns `"id"` field — same as defect #16. | Unexpected `"id"` key in response objects. | Excluded `_id` in the projection; `format_attendance_record()` does not include it. |
| 27 | `list_attendance()` | Returns raw datetimes instead of epoch milliseconds. | Same class of bug as #19. | Applied `format_attendance_record()`. |
| 28 | Startup | **No indexes created.** No unique index on `emp_code`, no compound index on `(emp_code, date)`. Concurrency guarantees are impossible, and queries are full collection scans on large data. | Concurrent duplicates succeed; analytics queries time out on 100k records. | Added `create_indexes()` on startup with all required indexes. |

## Not a defect

| What I examined | Why it is fine |
|---|---|
| `PunchInIn.status` default `"PRESENT"` | Matches the OpenAPI spec default. |
| `load_dotenv()` at module level | `python-dotenv` docs say real env vars take priority by default, so this satisfies the "real environment variables must win" rule. |
| `IST = timezone(timedelta(hours=5, minutes=30))` | Correct fixed offset for IST; no DST transitions to worry about. |
